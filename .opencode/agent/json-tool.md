# What json-tool is

json-tool is a privacy-first JSON formatter, validator and beautifier. It does
not track users, does not store their data and does not sell their data.
Formatting runs in a Web Worker so the UI stays responsive. It is built with
React 19, TypeScript, Tailwind CSS and CodeMirror, and ships as a web app and
an Electron desktop app.

Features:
- JSON validation with an error message for invalid JSON.
- Formatting / beautifying with configurable indentation (default 2 spaces).
- Clipboard paste and copy.
- Upload a JSON file.
- Search inside the editors (CodeMirror).
- JSON as a table view.
- JSON shape and statistics view.
- Dark mode and a history drawer.
- Full keyboard support: every action has a shortcut, and `?` opens the
  shortcut list for the current page.

Docs live in `README.md` and in the VitePress documentation under `docs/`
(user manual, published under `/docs` on GitHub Pages). The VitePress site is
built with `pnpm docs:build` and its screenshots are generated by
`scripts/screenshots.mjs` (`pnpm docs:screenshots`). The application routes are
defined in `src/App.tsx`, and the header shows a "Docs" link to the hosted
documentation.

# How to run and use the app

Scripts (see `package.json`):
- `pnpm install` - install dependencies.
- `pnpm start` - start the Vite dev server.
- `pnpm dev` - run Vite and Electron together.
- `pnpm build` - production build into `build/`.
- `pnpm test` - run the Jest unit/component tests.
- `pnpm coverage` - run tests with coverage.
- `pnpm lint` - run ESLint over `src/**/*.{ts,tsx}`.
- `pnpm lint:fix` - ESLint with autofix.
- `pnpm docs:dev` / `pnpm docs:build` / `pnpm docs:preview` - VitePress docs
  dev server, build and preview.
- `pnpm docs:screenshots` - regenerate the documentation screenshots with
  Playwright (writes to `docs/public/screenshots`).
- `pnpm e2e` / `pnpm e2e:open` - run / open the Cypress end-to-end tests.
- `pnpm serve` - serve the production build.

Make targets (see `Makefile`): `make build`, `make start`, `make e2e`,
`make clean`, and `make before-push BUIL_APP=true START_APP=true RUN_E2E=true`.

Using the app:
1. Open the app and paste or type JSON into the working editor on the left.
2. Use the header tabs to switch views:
   - home (`/`) - format/validate editors.
   - table (`/table`, test id `table`) - JSON as a table.
   - shape (`/schema`, test id `schema`) - JSON shape and statistics.
   - settings (`/settings`). The docs are external (header "Docs" link).
3. Toggle "validate json" and dark mode from the header.

# Keyboard support and shortcuts

Keyboard support is a first-class feature. When adding or changing an action,
follow the existing keyboard definitions instead of inventing new key handlers.

- The shortcut registry in `src/ShortcutsContext.tsx` is the source of truth and
  `src/components/ui/KeyboardShortcuts.tsx` renders the `?` dialog from it. The
  user-facing list is `docs/guide/keyboard.md`. Read those files before answering
  or adding shortcuts; do not duplicate the list here.
- Register actions with
  `useShortcut({ id, keys, description, section, handler, enabled })`.
  Do not add ad-hoc `window.addEventListener('keydown', ...)` handlers in
  components.
- Use `Mod+<key>` for cross-platform shortcuts (`Ctrl` on Windows/Linux, `⌘` on
  macOS). Shortcuts are matched against both `event.code` and `event.key`.
- The registry listens in the capture phase so shortcuts work while a CodeMirror
  editor is focused. CodeMirror must not swallow them.
- Use `ignoreWhileTyping` only for printable shortcuts such as `?`, so typing in
  an editor still works.
- Keep `indentWithTab={false}` in `src/components/ui/editor/JsonEditor.tsx` so
  Tab moves focus out of an editor instead of inserting indentation.
- Reuse an existing shortcut when one already covers the action. Before adding a
  new shortcut, check `src/ShortcutsContext.tsx` and `docs/guide/keyboard.md`
  to avoid conflicts.

When asked how to perform an action, use the documented shortcut from the
registry/docs rather than guessing. When adding an action, register its shortcut,
update the keyboard docs and add Jest/Cypress coverage.

# Testing conventions

Tests are feature-first: keyboard coverage belongs to the feature it changes,
not to a separate keyboard suite.

Follow the existing test helpers; do not reach into the DOM with brittle index
lookups.

- Render with `renderEntireApp()` from
  `src/__test__/__testutilities__/builder.tsx`.
- Query editors with `grabCurrentEditor(container)` for the working editor and
  `grabResultEditor(container)` for the result editor. For other editors use
  `grabEditor(container, testId)`. These live in
  `src/__test__/__testutilities__/editorQuery.ts`.
- **Never** use `document.querySelectorAll('.cm-content')[0]`,
  `[1]`, or any indexed `.cm-content` lookup in tests. Use the editor helpers.
- Use `customType(editor, text)` from
  `src/__test__/__testutilities__/customTyping.ts` to type into an editor.
- Use the existing test ids and `screen.getByTestId` / `within`. Prefer
  `data-testid` over CSS structure.
- Clipboard tests use `setUpClipboard`, `tearDownClipboard`,
  `writeTextToClipboard` and `readTextFromClipboard` from `jest-clipboard`.
  Restore `window.matchMedia` with `matchMedia(false)` / `emptyMatchMedia()`.
- Keyboard Jest tests use `fireEvent.keyDown(window, ...)` or
  `userEvent.keyboard(...)`, then assert focus with `toHaveFocus()`.
- Cypress keyboard steps must dispatch a native `KeyboardEvent` on the active
  element (see `pressKey` in `cypress/support/keyboard.js`). Do not use
  `cy.get('body').trigger('keydown', ...)`; it does not reach the window
  listener reliably.
- Put keyboard scenarios in the owning Cypress feature (for example
  `Clipboard.feature`, `JsonTable.feature`, `JsonShape.feature`,
  `UserInterface.feature`) and add feature-specific assertions to that
  feature's step definitions. `KeyPressSteps.js` only holds shared key-press
  steps; do not put feature-specific assertions there.
- Put Jest keyboard coverage in the test file for the feature being changed (for
  example `Editors.test.tsx`, `Clipboard.test.tsx`, `CleanUpEditors.test.tsx`,
  `CleanUpJsonString.test.tsx`, `CleanUpJsonNewLines.test.tsx`,
  `CustomSpacing.test.tsx`, `JsonToTable.test.tsx`, `Shape.test.tsx`,
  `UiElements.test.tsx`, `UsedJsonHistory.test.tsx`, `Documentation.test.tsx`,
  `DarkMode.test.tsx`, `Settings.test.tsx` or `Diff.test.tsx`).
- Do not create standalone keyboard test suites such as
  `KeyboardNavigation.test.tsx` or `KeyboardNavigation.feature`. Add the
  coverage to the feature that owns the action.
- When changing keyboard behavior, update `docs/guide/keyboard.md` and the
  README shortcut section, then run `pnpm test`, `pnpm lint`, `pnpm build`,
  `pnpm docs:build` and the affected Cypress features.

# JSON shape and statistics feature

Route `/schema`, header tab test id `schema`, page title "JSON shape"
(`src/pages/Schema.tsx`). Paste JSON into the working editor and the right
pane shows an aggregate analysis of the whole document plus the same analysis
for every nested object/array shape.

Core logic - `src/core/jsonToSchema.ts`:
- `analyzeShapeReport(value): ShapeNode` - builds the full report tree. The
  root node holds the overall statistics; each nested object/array path gets a
  child node with the same statistics scoped to that shape, recursively.
- `analyzeShapeStatistics(value): ShapeStatistics` - statistics for a single
  value.
- `typeNameOf(value)` - JSON type name (`string`, `number`, `boolean`, `null`,
  `object`, `array`).
- `isEmptyValue(value)` - a value is empty when it is `null`, `""`, `[]` or
  `{}`.

`ShapeStatistics` fields:
- `objects` - total objects in the subtree.
- `arrays` - total arrays in the subtree.
- `properties` - distinct property names.
- `values` - total values (property values plus array elements).
- `filled` / `empty` - counts of non-empty vs empty values.
- `averageProperties` - property values per object.
- `typeCounts` - array of `{ type, count, percentage }` sorted by count.

`ShapeNode` fields: `path`, `kind` (`object` | `array` | `scalar`),
`typeName`, `count` (instances at that path), `statistics`, `children`.

Behavior details:
- Array elements and property values are both counted as values.
- Repeated shapes are aggregated into a single node (for example, 32 objects
  with an `author` field produce one `author` node with `count: 32`).
- A nested shape appears only under its parent path; paths are never
  duplicated across levels.
- Fields inside an array are measured against the number of elements; nested
  objects inherit the enclosing population, so percentages never exceed 100%.

UI - `src/components/ui/schema/JsonShapeStatistics.tsx`:
- Renders the high-level statistics panel (stat cards plus a type breakdown
  table) and a "Nested shapes" section.
- Each nested shape is a collapsible `<details>` with its path, type badge,
  instance count, the full statistics panel and recursively nested children.
- Expand all / Collapse all buttons control every nested shape at once
  (test ids `json-shape-expand-all` and `json-shape-collapse-all`).
- Test ids: `json-shape`, `json-shape-nested`, `json-shape-node`,
  `json-shape-node-path`, `json-shape-node-type`, `json-shape-node-count`, and
  the card/table ids prefixed with `json-shape` or `json-shape-node`.

Page test ids: `schema-title`, `schema-page`, `schema-json`, `schema-pane`,
`schema-container`, `schema-error`, `schema-empty`.

Tests for this feature:
- `src/__test__/core/jsonToSchema.test.ts` - core statistics and report tree.
- `src/__test__/components/JsonShapeStatistics.test.tsx` - component rendering.
- `src/__test__/Shape.test.tsx` - page behavior.
- `cypress/e2e/JsonShape.feature` and
  `cypress/support/step_definitions/JsonShapeSteps.js` - end-to-end.
